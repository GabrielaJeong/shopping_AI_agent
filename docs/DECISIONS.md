## D-001: 스택 = TypeScript + Next.js(App Router) 단일 앱

**날짜**: 2026-06-03
**버전**: v0.0
**상태**: 적용 중
**결정**: TypeScript + Next.js(App Router) 단일 앱. 백엔드는 별도 서버 없이 Next.js API 라우트로 통합. 스타일링 Tailwind, 패키지 매니저 pnpm. 타깃은 웹(모바일 셸).
**대안**: React Native / Expo, SwiftUI 등 모바일 네이티브 (handoff 문서가 "스택 자유 선택"으로 열어둔 옵션).
**근거**: 사이드 프로젝트 0→1 속도와 단일 코드베이스에서 UI+API 통합 운영이 유리. handoff의 "스택 자유 선택" 지시는 이 결정으로 확정 대체한다.
**트레이드오프**: 진짜 네이티브 앱 경험(제스처/성능/스토어 배포) 포기. 모바일 셸 레이아웃(390×844 캔버스, 54px safe-area)을 웹에서 재현해야 함.
**PRD 연결**: 전 기능의 구현 토대 — 특히 F5(추천 UI·피드백 시트)와 F4(AI 챗 시트)를 웹 모바일 셸에서 구현.

## D-002: 단계적 구현 — UI 충실 재현 먼저, 추천/챗봇/피드백 로직은 mock

**날짜**: 2026-06-03
**버전**: v0.0
**상태**: 적용 중
**결정**: 현재 단계는 디자인 정본대로 UI를 충실히 재현하고, 추천·챗봇·피드백 로직은 mock으로 둔다. 실제 로직은 PRD F2~F6 명세대로 이후 단계에서 새로 구현(LLM 챗봇도 지금은 UI/목, 실제 연동은 뒤 단계).
**대안**: 처음부터 추천 파이프라인/LLM을 함께 구현. 또는 프로토타입의 키워드 라우팅을 그대로 채택.
**근거**: UI와 로직을 분리하면 화면을 빠르게 세우면서, 추천 인터페이스를 PRD 명세를 향해 점진 교체할 수 있다. 콜드스타트를 기본 출발 상태로 두는 PRD 로드맵(Phase 0→1→2)과도 정합.
**트레이드오프**: mock 인터페이스가 F2~F6 실제 형태와 어긋나면 후속 교체 비용 발생 → mock도 PRD 입출력 계약을 향하도록 설계해 위험을 줄인다.
**주의**: 프로토타입의 키워드 라우팅을 "정답"으로 박지 말 것.
**PRD 연결**: 지금은 F1(온보딩)·F5(추천 UI·피드백 시트) UI를 충실히 재현, F2~F4·F6 로직은 이후 단계(mock 인터페이스가 PRD 입출력 계약을 향하도록).

## D-003: 데이터베이스 = Phase 0 PostgreSQL 단일 (초기 mock, 연결은 이후)

**날짜**: 2026-06-04
**버전**: v0.0
**상태**: 적용 중
**결정**: Phase 0은 PostgreSQL 단일 DB로 간다. 초기 단계는 mock 데이터로 동작하고 실제 DB 연결은 이후. 카탈로그/로그가 비대해지면 분리를 고려하고, 벡터 검색이 필요해지면 pgvector를 얹는다.
**대안**: NoSQL(문서/키-값) 우선, 또는 처음부터 다중 저장소 분리. handoff 프로토타입의 localStorage 영속화.
**근거**: 추천 핵심 데이터(유저·상품·이벤트)는 다대다 관계라 관계형이 유리하다. "추천=NoSQL"은 오해 — 조인·정합성이 중요한 도메인이다. handoff의 localStorage 영속화는 프로토타입 스캐폴딩이므로 따르지 않는다(D-001 참조).
**트레이드오프**: 초대형 카탈로그/로그 스케일에서는 단일 PostgreSQL이 병목이 될 수 있음 → 그 시점에 분리/전용 저장소로 진화. 벡터 검색은 pgvector로 후행 도입.
**PRD 연결**: F1(취향 벡터 시드 저장), F2(상품 카탈로그), F6(취향 벡터 갱신·이벤트 신호 영속화)의 저장 계층. (PRD §3-1 데이터 계층)

## D-004: 추천 파이프라인 = 데이터 성숙도에 따른 단계 전환

**날짜**: 2026-06-04
**버전**: v0.0
**상태**: 적용 중
**결정**: 후보 생성과 랭킹을 데이터 성숙도에 따라 단계적으로 전환한다. 후보 생성: 출시 단계 콘텐츠+규칙 → 데이터 축적 후 협업 필터링(CF) 추가. 랭킹: 출시 단계 수동 가중합 → 데이터 축적 후 학습 기반(GBDT/LTR).
**대안**: 처음부터 학습 기반 모델 도입(데이터 부족으로 비현실적), 또는 단일 전략 고정.
**근거**: 출시 시점엔 행동 데이터가 거의 없으므로 콘텐츠+규칙이 즉시 동작하고 신규 상품 콜드스타트에 강하다. 골격(후보 생성→랭킹 2단계)을 유지한 채 내부 전략만 교체하면 인터페이스가 안정적으로 유지된다.
**트레이드오프**: 단계 전환마다 재구현/검증 비용. 초기 추천 품질은 수동 가중치 한계에 묶임 → reason 설명가능성으로 신뢰 보완.
**PRD 연결**: F2(후보 생성 — 콘텐츠/규칙/CF), F3(랭킹 모델 & match·reason — 가중합→학습). (PRD §6 단계적 출시 로드맵)

## D-005: 콜드스타트 = 예외가 아니라 기본 출발 상태

**날짜**: 2026-06-04
**버전**: v0.0
**상태**: 적용 중
**결정**: 콜드스타트를 예외 처리가 아니라 시스템의 기본 출발 상태로 설계한다. 온보딩으로 취향 벡터를 시드하고, 콘텐츠+규칙 기반으로 100% 동작을 시작한 뒤 데이터 성숙도에 따라 CF·학습 모델로 점진 전환한다. 온보딩을 건너뛴 사용자도 빈 화면 없이 인기·신상 규칙 기반으로 시작.
**대안**: 콜드스타트를 별도 예외 분기로 취급(데이터 쌓일 때까지 추천 빈약/공백 허용).
**근거**: 출시 시점엔 데이터가 거의 없는 게 정상이므로, 콜드스타트를 정상 경로로 두어야 첫 세션부터 추천이 작동한다. 신규 유저·신규 상품·신규 서비스 세 종류 모두를 출발 상태로 흡수.
**트레이드오프**: 초기 추천은 개인화 깊이가 얕음(규칙·콘텐츠 의존) → 피드백 루프(F6)로 빠르게 정확도를 끌어올린다.
**PRD 연결**: F1(온보딩 취향 벡터 시드)과 F2(콘텐츠+규칙 폴백)가 신규 유저·상품·서비스 콜드스타트를 함께 해소. (PRD §3-2, F1·F2 콜드스타트 동작)

## D-007: Next.js 버전 = 15.x로 고정 (16 아님)

**날짜**: 2026-06-04
**버전**: v0.0
**상태**: 적용 중
**결정**: Next.js를 15.x(스캐폴드 시점 15.5.19)로 고정한다. `create-next-app@latest`가 기본 제공하는 16.x는 채택하지 않는다. React 19.1, Tailwind v4, App Router, src 디렉터리, pnpm 구성.

**트레이드오프**: 16 전용 신기능 미사용. 추후 16으로 올릴 때 마이그레이션 비용 발생 가능.
**PRD 연결**: 특정 F 아님 — 전 기능의 구현 토대(D-001 스택 결정의 버전 확정). 16 채택 시엔 매 작업 전 번들 docs 확인이 강제됨.

## D-008: 디자인 토큰 = Tailwind v4 `@theme` (CSS-first), 폰트는 Pretendard CDN

**날짜**: 2026-06-04
**버전**: v0.0
**상태**: 적용 중
**결정**: 프로토타입 `styles.css`의 토큰을 `src/app/globals.css`의 `@theme` 블록에 1:1 이식한다(색 `--color-*`, radius `--radius-*`, shadow `--shadow-*`, 텍스트 스케일 `--text-*` + line-height/letter-spacing/weight 모디파이어). `tailwind.config.js`는 만들지 않는다(Tailwind v4는 CSS-first). 간격은 Tailwind 기본 스케일(4px step)을 그대로 쓴다. Pretendard는 jsDelivr 동적 서브셋 CSS를 `layout.tsx`에서 `<link>`로 로드, 워드마크용 `--font-brand`(Helvetica/Arial) 별도.
**대안**: (1) `tailwind.config.ts`에 토큰 정의(v3 방식) — v4에선 비표준. (2) `.t-display` 등 프로토타입 유틸리티 클래스를 그대로 포팅 — 토큰화 이점 상실. (3) Pretendard를 next/font/local로 자가호스팅 — 폰트 파일 관리 부담.
**근거**: v4 표준인 `@theme`가 `bg-paper`/`text-h1`/`rounded-card` 등 유틸리티를 자동 생성해 토큰을 단일 출처로 둘 수 있다. 빌드 산출 CSS에 유틸리티 생성을 확인함. CDN 동적 서브셋은 한글 우선 가변폰트를 적은 설정으로 로드.
**트레이드오프**: 외부 CDN(jsDelivr) 의존 — 오프라인/CDN 장애 시 폴백 폰트로 렌더. 필요 시 next/font/local 자가호스팅으로 전환 가능. radius `--radius-sheet`는 styles.css 실제값 18px 채택(README 표의 20px와 불일치 — 구현값 우선).
**PRD 연결**: 특정 F 아님 — F1·F4·F5 등 전 화면의 시각 토대. 디자인 정본(README)의 토큰 테이블을 코드로 고정.

## D-009: 앱 구조 = 단일 루트 클라이언트 상태 머신 + mock 영속화 추상화

**날짜**: 2026-06-05
**버전**: v0.0
**상태**: 적용 중
**결정**: handoff의 런치 머신(`splash → intro → login → onboarding → app`)을 **단일 루트의 클라이언트 상태 머신**으로 구현한다(라우트 분리 X). `AppStateProvider`(`src/lib/app-state.tsx`)가 `stage`와 전이(`finishSplash`/`finishIntro`/`login`/`finishOnboarding`/`logout`/`resetOnboarding`)를 보유하고, `AppRoot`가 현재 stage를 렌더한다. 온보딩 완료 플래그는 **mock 영속화 레이어**(`src/lib/persistence.ts`, `PersistenceStore` 인터페이스)로 추상화 — 지금은 localStorage(`moodyfit_onboarded`) 백엔드, 나중에 서버/DB로 구현만 교체(D-003). `app` 스테이지 내부의 tab/screen/sheet 라우팅은 app 구현 단계에서 확장.
**대안**: (1) App Router 실제 라우트(`/onboarding` 등)로 스테이지 분리 — 모바일 셸 전환 애니메이션·전역 상태 공유가 번거롭고 프로토타입과 멀어짐. (2) localStorage 직접 호출 — DB 교체 시 호출부 전수 수정 필요(영속화 추상화로 회피).
**근거**: 모바일 셸 단일 캔버스 특성상 단일 상태 머신이 프로토타입 동작과 가깝고 시트/푸시 전환 제어가 쉽다. 영속화 인터페이스화로 D-003(Phase 0 mock → 이후 DB) 전환 비용을 한 파일로 가둠.
**트레이드오프**: 단일 상태가 커질 수 있음 → app 스테이지의 tab/screen/sheet는 별도 컨텍스트/리듀서로 분리 예정. stage가 URL에 반영되지 않음(딥링크/뒤로가기 제약) — 필요해지면 라우팅 동기화 재검토.
**PRD 연결**: F1(온보딩 게이트 = `moodyfit_onboarded` 영속), 그리고 전 화면의 진입 흐름(런치 → app)의 골격.

## D-010: 취향 벡터 구조 = 태그→가중치 맵 + 별도 예산, 시드는 수동 휴리스틱

**날짜**: 2026-06-05
**버전**: v0.0
**상태**: 적용 중

## D-013: 피드백 반영 경계 = `applyFeedback(taste, product, signal)` → 갱신 프로필 + 변화

## D-014: 챗봇 재랭킹 경계 = 발화→조건(parse) + 조건→결과(rerank) 두 함수 분리

**날짜**: 2026-06-05
**버전**: v0.0
**상태**: 적용 중
**결정**: 챗봇 재랭킹(F4)을 `lib/chat-rerank.ts`의 **두 경계 함수**로 분리한다(UI 분리, D-001).
`parseReorderIntent(utterance, ctx) → ReorderConditions`(톤·실루엣·가격상한·브랜드·가중치 조정 + 원본 발화; ctx는 취향 벡터·현재 상품)와 `rerank(conditions, taste) → Recommendation[]`(match·reason 포함). 시트는 발화 → parse → rerank → 결과 카드를 AI 버블에 인라인. **방향성**: 챗봇이 올리는 것은 점수가 아니라 **조건(ReorderConditions)**, `match`·`reason`은 rerank가 돌려주는 **결과**. 현재 parse는 키워드 mock(이후 LLM 의도 파싱), rerank는 조건 필터+가중 정렬 mock(이후 F3 랭킹 엔진). 타이핑 인디케이터는 연출.
**대안**: (1) 프로토타입의 "키워드→고정 응답(canned products)" 라우팅 부활 — 명시적으로 금지(D-002 주의). 조건 산출 없이 가짜 응답이라 교체 경로가 안 생김. (2) parse+rerank를 한 함수로 — 발화 이해와 랭킹은 책임이 달라 분리(LLM ↔ 랭킹 엔진은 다른 시스템).
**근거**: PRD F4의 "발화 → 재랭킹 조건(↑) → 재정렬 결과(↓)" 양방향 루프를 코드 구조로 고정. mock이되 "진짜 구조의 형태"라, LLM/랭킹 엔진은 각 함수 속만 채우면 됨. 조건이 1급 객체라 멀티턴 누적·가중치 매핑으로 확장 가능.
**트레이드오프**: mock parse/rerank 품질은 낮음(키워드·단순 점수식). reason은 조건 템플릿(HTML) — F3의 "최대 기여 피처" 생성과는 다르며 추후 대체. 재랭킹 결과 match는 rerank의 mock 점수라 Home/detail의 정적 더미 match와 출처가 다름(의도된 것 — 재랭킹은 결과를 계산).
**PRD 연결**: **F4**(LLM 챗봇 재랭킹)의 두 방향(parse=조건 올리기, rerank=결과 받기) 경계. F3 랭킹과 LLM 의도 파싱이 각각 들어올 자리.

## D-015: 스크롤 위치 = 단일 컨테이너 + 수동 위치 관리(표준 모바일)

**날짜**: 2026-06-11
**버전**: v0.0
**상태**: 적용 중
**결정**: app 셸은 화면(home탭/detail/list/search)을 **단일 `overflow-y-auto` 컨테이너** 안에서 교체한다(화면별 스크롤 컨테이너를 두지 않음). 컨테이너가 언마운트되지 않아 `scrollTop`이 내비게이션에 걸쳐 남으므로, `AppShellInner`에서 **수동으로 위치를 관리**한다(표준 모바일 동작):
푸시 화면(detail/list/search) 진입·**탭 전환**은 맨 위(`scrollTop=0`)에서 시작하고, 푸시에서 `back`으로 탭 홈에 복귀할 때만 **직전 스크롤 위치를 복원**한다. 구현: 탭별 위치를 `Map<Tab, number>`에 `onScroll`로 기록(탭 홈을 볼 때만), `useLayoutEffect`(페인트 전)에서 `screen`이 푸시→home으로 바뀐 경우(=back)만 복원하고 그 외엔 0.
**대안**: (1) 화면마다 별도 스크롤 컨테이너(프로토타입 `.app-scroll`처럼) — 각자 스크롤이 자연 보존되나, 고정 높이 셸(`h-dvh`)·하단 내비·시트 오버레이와의 flex 체인이 복잡해지고 sticky 헤더 처리가 화면마다 중복. (2) 아무것도 안 함(현 단일 컨테이너 그대로) — 푸시/탭 전환이 직전 오프셋부터 열리는 버그(이번 수정 대상). (3) 항상 맨 위 리셋 — 단순하지만 back 시 탭 위치를 잃어 모바일 관습 위반.
**근거**: 단일 컨테이너는 셸 레이아웃(D-011)·sticky 헤더·시트와 가장 단순하게 맞물린다. 위치 관리만 수동으로 얹으면 "푸시=맨 위, back=복원"이라는 모바일 표준을 적은 코드로 만족. 시트 open/close는 `screen`/`tab`을 안 바꾸므로 effect가 안 돌아 배경 스크롤이 보존된다(시트 점프는 별개로 처리 — L-006).
**트레이드오프**: 탭 전환은 항상 맨 위(탭별 스크롤을 유지하지 않음) — 의도된 선택이나, 추후 "탭 스크롤 유지"를 원하면 `back` 분기 대신 탭 키별 복원으로 확장 가능. 위치 기록을 `onScroll`에 의존하므로, 프로그램적 스크롤(복원)도 한 번 기록되나 멱등이라 무해.
**PRD 연결**: 직접 대응 기능 없음(UX 기반). 내비게이션 플로우(런치 머신/푸시·back) 위에서 동작.

## D-016: 시트 상태 = AppShell 컨텍스트에서 분리한 별도 컨텍스트

(D-011의 "런치↔셸 컨텍스트 분리" 원칙의 연장 — 구독 단위를 더 쪼갬)
**대안**: (1) 단일 컨텍스트 유지(기존) — 시트 open이 `useAppShell` 소비 화면 전체를 재렌더. (2) 각 화면을 `React.memo` — 화면이 `useAppShell()`을 구독하는 한 컨텍스트 값 변경 시 재렌더되므로 효과 없음. (3) 시트를 별도 상태 라이브러리로 — 과함.
**근거**: 측정으로 확인 — 시트를 열면 `useAppShell` 컨텍스트 값이 바뀌어 **무거운 Home(히어로 슬라이더+다수 카드/이미지)이 재렌더**되고, 그 비용이 시트 슬라이드업 300ms 동안 메인 스레드를 막아 애니메이션이 끊겼다(홈에서만; 가벼운 detail은 매끄러움). 시트 상태 구독 범위를 오버레이로 좁히면 화면은 시트 토글에 재렌더되지 않아 슬라이드가 매끄럽다. (시트 점프=조상 스크롤은 별개 원인 — chat-sheet scrollIntoView 제거, L-006/L-007)
**트레이드오프**: 컨텍스트가 둘로 늘어 시트 상태를 읽으려면 `useSheet()`를 써야 함(현재 소비처는 `SheetOverlay`/`SheetContainer`뿐). 화면 컴포넌트가 실수로 `useSheet()`를 구독하면 다시 재렌더되므로, 시트 상태는 오버레이 밖에서 읽지 않는다(주석/이 결정으로 고정).
**PRD 연결**: 직접 대응 기능 없음(렌더 성능/UX). 두 핵심 시트(F4 챗·F5/F6 피드백)의 열림 품질에 영향.
