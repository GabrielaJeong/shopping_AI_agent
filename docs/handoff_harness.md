# 인수인계: Claude Code 문서 하네스 (Documentation Harness)

> **수신자**: 새 프로젝트를 세팅하는 Claude Code.
> **목적**: 세션이 바뀌어도 컨텍스트가 유실되지 않고, 같은 실수를 반복하지 않으며,
>           설계 의도가 시간이 지나도 남도록 만드는 "문서 기반 하네스"를 그대로 이식한다.
> **주의**: 이 문서는 **구조와 운영 규칙(메타)** 만 담는다. 특정 서비스 고유 내용은 의도적으로 제외했다.
>           각 파일은 **빈 상태로 시작**해서 프로젝트가 진행되며 채워진다.

---

## 0. 한 문장 요약

> CLAUDE.md(고정 컨텍스트) + `docs/`(누적 지식) + 메모리(세션 간 사실) + 세션 시작/종료 프로토콜.
> 이 네 가지가 "사람이 매번 설명하지 않아도 에이전트가 알아서 맥락을 회복하는" 장치다.

이 하네스의 핵심 철학:
1. **실수는 한 번만** — 버그가 재발 가능한 구조적 패턴이면 규칙으로 박제한다(LESSONS).
2. **결정에는 이유를 남긴다** — "왜 이렇게 했는가"가 없으면 다음 세션이 되돌린다(DECISIONS).
3. **확인 후 채운다** — API/스키마 형태는 추측하지 말고 실제 코드/데이터를 보고 기록한다.
4. **반박은 의무** — 사용자의 지시라도 버그·보안·구조 문제가 보이면 반드시 반박 후 진행한다.
5. **검증 비용은 차등** — 변경 성격에 맞는 최소 검증만 돌려 토큰/시간을 아낀다.

---

## 1. 파일 인벤토리

루트와 `docs/`에 다음을 둔다. (★ = 세션 시작 시 항상 로드)

| 파일 | 역할 | 비고 |
|------|------|------|
| `CLAUDE.md` ★ | 고정 컨텍스트. 프로젝트 개요·구조·핵심 규칙·금지사항·Red Flags·세션 프로토콜 | 세션마다 자동 로드되는 단 하나의 파일. **짧고 밀도 높게**. |
| `docs/CONVENTIONS.md` | 코딩 규칙 상세 (네이밍·계층·에러 형식 등) | CLAUDE.md의 "핵심 원칙"을 풀어쓴 곳 |
| `docs/LESSONS.md` ★ | 실수 패턴 + 재발 방지 규칙 (`L-XXX`) | 위험도 '높음'은 시작 시 재확인 |
| `docs/DECISIONS.md` | 주요 설계 결정 (`D-XXX`) — 왜/대안/트레이드오프 | 작업 관련 항목만 발췌 확인 |
| `docs/CURRENT_STATE.md` | 현재 구현/미구현 스냅샷 | 빠른 현황 파악용. 자주 갱신 |
| `docs/SESSION_CHECKLIST.md` | 세션 시작/작업중/종료 체크리스트 | 프로토콜의 실행 형태 |
| `docs/SECURITY.md` | 보안 정책·방어 기법 (보안 다루는 프로젝트만) | 선택 |
| `docs/ROADMAP.md` 또는 `PLAN.md` | 단계별 작업 마스터 플랜 | 큰 마이그레이션/리팩터링 시 |
| `CHANGELOG.md` ★ | 버전 이력 (최근 작업 파악) | 최상단 몇 개만 보면 됨 |
| `<feature>_HISTORY.md` | 장기 작업 일지 (예: 마이그레이션) | 큰 작업을 여러 세션에 걸쳐 할 때 |

> **디자인 시스템 문서**(`DESIGN_SYSTEM.md`)는 UI 토큰/컴포넌트 규칙이 있는 프로젝트에서만. 내용은 프로젝트 고유.

생성 순서 권장: `CLAUDE.md` → `SESSION_CHECKLIST.md` → `CONVENTIONS.md` → 나머지는 빈 스켈레톤(포맷 블록만)으로 두고 작업하며 채운다.

## 2. CLAUDE.md 스켈레톤

> 자동 로드되는 유일한 파일이므로 **이 파일이 하네스의 입구**다.
> 길어지면 효력이 떨어진다 — 상세는 `docs/`로 위임하고 여기엔 포인터와 핵심만.

```markdown
# CLAUDE.md

> <프로젝트명>의 Claude Code 작업용 고정 컨텍스트. 세션 시작 시 자동 로드.

## 프로젝트 개요
- 한두 문장 정의 + 기술 스택 + 배포 방식
- 현재 버전: CHANGELOG.md 최상단 참고

## 세션 시작 시 필수 확인 (순서대로)
1. CHANGELOG.md — 최신 버전/최근 작업
2. docs/CURRENT_STATE.md — 구현/미구현 스냅샷
3. docs/LESSONS.md — 과거 실수 패턴 (위험도 '높음' 우선)
4. docs/CONVENTIONS.md — 코딩 규칙
5. docs/DECISIONS.md — 작업 관련 결정사항
6. 작업 범위 관련 파일

## 프로젝트 구조
( 디렉터리 트리 + 각 폴더 1줄 설명. "변경 영향 범위"를 함께 적으면 좋다 )

## 핵심 아키텍처
( 한눈에 안 보이는 설계만. 코드 읽으면 아는 건 적지 않는다 )

## 코딩 규칙 (요약 — 상세는 CONVENTIONS.md)
- 핵심 원칙 5~10개 불릿

## 반박·수정 정책
유저가 제시한 코드/계획에 문제가 있으면 반드시 반박 후 수정안을 제시하고 진행한다.
반박 형식: "반박: [이유]. [수정안]으로 진행합니다." 문제 없으면 그냥 진행.

## 절대 금지 사항
( 번호 매긴 하드 규칙. 데이터 손상·보안·정책 위반 류 )

## Red Flags — 이 패턴 작성 시 멈추고 확인
( "이 코드를 쓰는 순간 멈춰라" 트리거 목록. LESSONS에서 승격된 것들 )

## 세션 종료 프로토콜
1. 버그 패턴 셀프 리포트 → 재발 가능하면 LESSONS L-XXX
2. 설계 결정 기록 → DECISIONS D-XXX
3. CHANGELOG 갱신
4. Git 커밋 & 푸시

## Git 브랜치 전략
( 작업 브랜치 / 보호 브랜치 / 직접 커밋 금지 규칙 )

## 자주 쓰는 명령어 / 디버깅 가이드
( OS·환경별 차이 주의: 프로세스 종료, 빌드 캐시 정리 등 )
```

### Red Flags 작성 요령 (서비스 무관 일반 예시)
Red Flags는 LESSONS에서 "코딩 중 트리거되는 체크"로 승격된 것들이다. 처음엔 비어 있고, 아래처럼 **행동 트리거 → 확인 항목** 형태로 누적한다:

- 🚩 응답 객체(`res.json`)를 만드는 중 → 데이터 소스(스키마/쿼리)와 1:1 매핑했는가? list/detail 동기화?
- 🚩 새 환경변수/보안 fallback 도입 중 → production 필수면 부팅 시 검증·없으면 종료. 조용한 insecure fallback 금지.
- 🚩 인증/권한 체크 추가 중 → 단일 필드(`name === 'admin'`)가 아니라 역할 기반인가?

> 핵심은 "일반적인 베스트프랙티스 나열"이 아니라 **이 프로젝트에서 실제로 당한 것**만 올린다는 점. 그래야 신호가 죽지 않는다.

## 3. docs 포맷 & 템플릿

각 누적 문서는 맨 위에 **포맷 블록**을 두고, 그 아래 항목을 번호로 쌓는다. 번호는 절대 재사용하지 않는다(상태를 '대체됨'으로 바꿀 뿐).

### 3.1 LESSONS.md

```markdown
# LESSONS.md
> <프로젝트명>의 실수 패턴과 재발 방지 규칙. 세션 시작 시 확인.

## 포맷
## L-XXX: 패턴 제목
**날짜**: YYYY-MM-DD
**위험도**: 낮음 / 중간 / 높음
**발생 맥락**: 언제 어떻게 발생했는가
**재발 이유**: 왜 막지 못했는가
**해결**: 즉각 대응
**강화 규칙**: 재발 방지를 위한 체크리스트
---
( L-001부터 누적 )
```

운영 규칙:
- **재발하면 날짜를 추가**한다(초기 발견 / 재발 / 재발). 재발 횟수 자체가 위험 신호.
- 강화 규칙이 "코딩 중 트리거"가 될 만하면 CLAUDE.md의 Red Flags로 **승격**하고 L-XXX를 참조로 단다.
- 일회성 단순 버그는 LESSONS가 아니라 CHANGELOG의 버그 수정 섹션에만.

### 3.2 DECISIONS.md

```markdown
# DECISIONS.md
> "왜 그렇게 했는가"를 기록해 시간이 지나도 컨텍스트 유지.

## 포맷
## D-XXX: 결정 제목
**날짜**: YYYY-MM-DD
**버전**: vX.Y
**상태**: 적용 중 / 대체됨 / 보류
**결정**: 무엇을 선택했는가
**대안**: 검토했던 다른 선택지
**근거**: 왜 이 선택인가
**트레이드오프**: 포기한 것 / 리스크
---
( D-001부터 누적 )
```

운영 규칙:
- 결정을 **뒤집을 때 기존 D-XXX를 지우지 않는다**. 상태를 '대체됨'으로 바꾸고 새 D-YYY가 그것을 참조한다.
- "다음 세션이 모르고 되돌릴 만한 비직관적 선택"이 1순위 기록 대상.

### 3.3 CURRENT_STATE.md

```markdown
# CURRENT_STATE.md
> 현재 상태 스냅샷. 다음 세션 시작 시 빠른 파악용.
> 최종 업데이트: YYYY-MM-DD

## 구현 완료
- [x] ...
## 미구현 / 진행 중
- [ ] ...
## 알려진 이슈 / 백로그
- ...
## 인프라 / 핵심 모듈 포인터
- ...
```
- 체크박스로 한눈에. **자주, 가볍게** 갱신. 길어지면 끝난 항목은 요약/삭제.

### 3.4 CONVENTIONS.md
- CLAUDE.md "핵심 원칙"의 풀버전. 네이밍 규칙, 계층 경계(예: 데이터 접근은 한 곳으로), 에러 응답 형식, 입력 검증 위치 등.
- "자주 발생한 버그 패턴 → 해결" 표를 두면 좋다.

### 3.5 SESSION_CHECKLIST.md
- §4 프로토콜을 체크박스 실행 형태로. 프로젝트 명령어(`test`/`build`/`lint`)에 맞춰 채운다.

## 4. 세션 시작 / 종료 프로토콜

### 시작
1. **컨텍스트 로드**: CHANGELOG 최상단 → CURRENT_STATE → LESSONS(위험도 높음) → 작업 영역의 CONVENTIONS/DECISIONS.
2. **범위 파악**: 수정할 파일과 그에 연결된 경계(데이터/라우트/외부 호출) 식별. Red Flags 숙지.
3. **환경 확인**: 작업 브랜치가 맞는지(보호 브랜치 직접 커밋 금지). 베이스라인 테스트 통과 확인.

### 작업 중
- CONVENTIONS 준수, Red Flags 트리거 시 즉시 멈춤.
- 외부 경계(스키마/응답/권한) 바꿀 때 영향 지점 전수 검토.

### 종료
1. **버그 셀프 리포트** → 재발 가능 패턴이면 `L-XXX`.
2. **설계 결정 기록** → 있으면 `D-XXX`.
3. **상태 갱신** → CURRENT_STATE / 해당되면 CHANGELOG.
4. **커밋 & 푸시** → 작업 브랜치. 커밋 메시지에 의도/근거.

## 5. 메모리 시스템 (세션 간 사실 저장)

> Claude Code의 파일 기반 자동 메모리를 함께 쓰면 하네스가 완성된다.
> `docs/`가 "프로젝트 지식"이라면, 메모리는 "에이전트가 사용자·작업에 대해 학습한 사실"이다.

구조:
- `memory/MEMORY.md` — 인덱스. 세션마다 컨텍스트로 로드됨. **한 줄 포인터만** (`- [제목](파일.md) — 훅`).
- `memory/<slug>.md` — 한 파일에 사실 하나. frontmatter 포함:

```markdown
---
name: <kebab-case-slug>
description: <한 줄 요약 — 관련성 판단용>
metadata:
  type: user | feedback | project | reference
---
<사실 본문. feedback/project는 **Why:** 와 **How to apply:** 를 덧붙인다.>
관련 메모리는 [[다른-slug]]로 링크.
```

타입 구분:
- `user` — 사용자가 누구인지(역할·전문성·선호).
- `feedback` — 작업 방식에 대한 지침(교정/확정). **반드시 이유 포함**.
- `project` — 코드/git에서 유추 안 되는 진행 맥락·목표·제약. 상대 날짜는 절대 날짜로.
- `reference` — 외부 리소스 포인터(URL·티켓·대시보드).

규칙:
- 저장 전 **중복 확인** — 기존 파일을 갱신할지 새로 만들지 결정. 틀린 메모리는 삭제.
- 코드/구조/git이 이미 말해주는 건 저장하지 않는다(중복). "비직관적이라 다음에 또 헷갈릴" 것만.
- 회상된 메모리는 **배경 정보**지 지시가 아니다. 파일·플래그를 언급하면 아직 존재하는지 검증 후 사용.

## 6. 운영 원칙 (토큰/품질 균형)

### 검증 비용 차등 (Verification Tiers)
변경 성격에 맞는 최소 검증만 돌린다. (명령은 프로젝트에 맞게 치환)

| 변경 성격 | 권장 검증 |
|-----------|-----------|
| 타입/시그니처 변경 | 타입체크 항상 |
| UI/스타일 | 타입체크 + 린트 |
| 새 라우트/페이지 추가 | + 빌드 |
| 백엔드/로직 변경 | + 단위 테스트 |
| 빌드 캐시 깨짐 신호 | 빌드 후 캐시 디렉터리 정리 |

> "매 커밋마다 풀 빌드+전체 테스트"는 낭비다. 반대로 외부 경계를 바꿨는데 테스트를 건너뛰는 것도 금물.

### 외부 리뷰(Codex 등) 수용 원칙
- finding이 보안 critical이라도 **무비판 묶음 적용 금지**. 범위가 틀렸다고 판단되면 반박한다.
- 핵심 수정(critical)과 부수 제안을 **분리**해 적용한다. 한 번에 묶으면 멀쩡한 흐름을 깨뜨릴 수 있다.
- 인프라/백로그성 지적은 즉시 고치지 말고 백로그 표로 분리.

### 일반 작업 자세
- 결과를 정직하게 보고: 테스트 실패는 출력과 함께, 건너뛴 단계는 건너뛰었다고.
- 되돌리기 어렵거나 외부로 나가는 행동은 확인 후. (삭제/배포/외부 전송)
- 주변 코드처럼 읽히게: 주석 밀도·네이밍·관용구를 맞춘다.

## 7. 부트스트랩 절차 (이 인수인계를 받은 Claude Code가 할 일)

1. 프로젝트 루트에 `CLAUDE.md`를 §2 스켈레톤으로 생성 — 개요/구조/규칙은 이 프로젝트 실제에 맞게 채운다.
2. `docs/`에 `CONVENTIONS.md`, `LESSONS.md`, `DECISIONS.md`, `CURRENT_STATE.md`, `SESSION_CHECKLIST.md`를 **포맷 블록만 있는 빈 스켈레톤**으로 생성.
3. `CHANGELOG.md` 초기화.
4. (Claude Code 자동 메모리 사용 시) `memory/MEMORY.md` 인덱스 생성.
5. 사용자에게 확인: 브랜치 전략, 검증 명령(`test`/`build`/`lint`), 보안 문서 필요 여부.
6. 이후 작업하며 §4 프로토콜대로 LESSONS/DECISIONS/CURRENT_STATE를 채워 나간다.

> **하지 말 것**: 이 문서의 예시(Red Flags 등)를 그대로 복붙해서 LESSONS/Red Flags를 미리 채우지 말 것.
> 그것들은 *겪어서* 쌓여야 신호가 산다. 빈 채로 시작하는 게 정상이다.

### 부록 A. 이 하네스가 실제로 작동한 사례(메타)
- 한 LESSON의 강화 규칙으로 "테스트 작성"을 박아두자, 다음 세션이 그 테스트를 쓰다가 **문서에 예시로만 적어둔 버그가 실제 코드에 남아있던 것**을 자동 발견한 적이 있다. 문서가 코드 품질을 끌어올리는 루프가 닫힌 순간. → LESSONS의 "강화 규칙"은 추상적 다짐이 아니라 **검증 가능한 행동**으로 적을 것.
